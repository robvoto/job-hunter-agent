# Alias Logic Rationale

---

## What aliases are for

Aliases are alternate terms that a job ad might use for the same capability.

Example: capability `"bpmn modelling"` might appear in job ads as `"business process modelling"`, `"bpmn 2.0"`, or `"process mapping"`. Without aliases, those ads would not score a match.

Aliases extend matching coverage without adding separate capabilities to the profile.

---

## Where aliases come from

1. **CV pipeline** (`cv_pipeline.py`): the deterministic phrase extractor clusters related phrases. The LLM renames cluster seeds but also passes raw aliases (cluster members) through.
2. **LLM CV extraction** (`profile_learning.py`): `_llm_extract_from_cv` generates capability entries with aliases from the full CV text.
3. **Manual user input**: the user can add or remove aliases in the settings UI.

All sources feed into `normalize_capability_rules` in `profile_store.py`, which calls `derive_job_description_aliases` to clean them.

---

## Validation rules (basic format only)

`_is_structurally_valid_alias` in `capability_matrix.py` enforces only:

- Not empty
- Max 4 tokens
- No duplicate tokens within the alias
- Each token at least 2 characters

**No token-overlap check against the canonical name.** An earlier version required 67% token overlap, which silently rejected all aliases for abbreviated capability names like `"bpmn modelling"` (aliases like `"business process modelling"` share only 1 of 3 tokens). That check was removed.

Do not re-introduce token-overlap gating. Aliases are generated by the LLM or entered by the user — both should be trusted after basic cleaning.

---

## Storage

Aliases are stored as a list of lowercase strings in `profile.json`:

```json
{
  "name": "bpmn modelling",
  "level": "strong",
  "aliases": ["business process modelling", "process modelling", "bpmn 2.0"]
}
```

Stored by `normalize_capability_rules` → `derive_job_description_aliases`.

---

## Downstream usage

- **Job matching** (`capability_matrix.py` → `expand_capability_terms`): returns name + all aliases as a flat list of searchable terms. The scorer checks all of them against the job ad.
- **LLM fit context** (`llm_gate.py` → `build_profile_prompt_context`): formats as `"name: level (alias1, alias2, ...)"` for the fit-scoring prompt.

---

## Known recurring failure mode

If `_is_structurally_valid_alias` is tightened (e.g. token-overlap check re-added), aliases silently disappear from all abbreviated or acronym-based capabilities. The UI shows `"No aliases yet."` / `"0 aliases"` with no error.

The function is marked SEALED in source. See `job_hunter_agent/capability_matrix.py`.
